# TLA+ Formal Verification (2026)

## 🎯 Purpose
Guidelines for mathematically verifying distributed systems and complex concurrent logic before implementation.

## 🛠️ The Process / Fact

### 1. Modeling Philosophy
- **Specification, Not Code:** Model *what* the system should do, not *how*. If your spec mirrors control flow (loops, `if` statements), it is too low-level.
- **PlusCal Gateway:** For teams new to formal methods, use PlusCal to write algorithmic logic, which translates into pure TLA+ for verification.

### 2. State Space Reduction (TLC)
- **Variable Economy:** Every variable multiplies the state space. Derive values using state functions (e.g., `WholeSet == S1 \cup S2`) instead of storing them.
- **Symmetry Sets:** Use symmetry sets in the `.cfg` file to treat identical processes (e.g., worker nodes) as mathematically equivalent, drastically reducing the states TLC must explore.
- **Action Agglomeration:** Combine consecutive atomic steps into a single TLA+ action if their interleaving does not affect correctness.

### 3. Model-Based Test Generation
- **Bridging the Gap:** Use the state-space graph generated by TLC to automatically create executable test cases (e.g., in Pytest or Rust) to ensure the implementation matches the verified math.

## ⚠️ Known Quirks or Edge Cases
- **Illegal Knowledge Passing:** TLA+ makes it easy for a process to accidentally read global state. Strictly audit your spec to ensure processes only act on data they would actually receive over a network.
- **Liveness Checking:** Checking for "liveness" (something good eventually happens) is slow. Separate safety (invariants) and liveness models to avoid bottlenecks.
